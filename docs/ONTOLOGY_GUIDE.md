# ONTOLOGY_GUIDE.md — что такое онтология и как её строить

Читать полностью перед созданием `docs/ONTOLOGY.md`. Единственный источник того, что в этом проекте понимается под онтологией.

---

## 1. Что это

Онтология — **модель предметной области на языке заказчика**. Отвечает на четыре вопроса:

1. **Что существует** в этой области (сущности).
2. **Что это означает** (определения).
3. **Как связано** (отношения).
4. **Что может происходить** и по каким правилам (действия, состояния, ограничения).

Описывает мир задачи так, как его видит автор ТЗ, — **до** решений о реализации.

## 2. Зачем она здесь — два применения

**При разработке.** Из онтологии выводятся: термины для промптов; tools — из действий; схемы — из сущностей и перечислений; проверки в коде — из бизнес-правил; задачи и тесты — из критериев приёмки. По ней проверяется, что из ТЗ ничего не потеряно и не придумано.

**В runtime.** Текст `ONTOLOGY.md` целиком подаётся в `ontology.check.ts` — модель по нему решает, относится ли запрос пользователя к предметной области бота (allow / clarify / reject). Разделы Назначение, Терминология и Границы попадают в system prompt агента. Бизнес-правила становятся предусловиями внутри tools.

Следствие для написания: разделы 1, 2, 9 должны быть сформулированы так, чтобы по ним можно было классифицировать чужой запрос. «Бот помогает с финансами» — плохо. «Бот отвечает на вопросы о транзакциях, категориях расходов и лимитах пользователя за выбранный период; не даёт инвестиционных советов и не работает с чужими счетами» — хорошо.

Ошибка в онтологии размножается во всё. Поэтому она делается первой и проверяется отдельно.

## 3. Чем онтология НЕ является

| Не онтология | Почему | Где этому место |
|---|---|---|
| TypeScript-интерфейсы, Zod, JSON schema | Реализация модели | `server/src/schemas/`, PLAN.md |
| Схема БД | Решение о хранении | PLAN.md |
| Endpoints, API | Транспорт | PLAN.md |
| React-компоненты, экраны | Интерфейс | PLAN.md |
| Названия и сигнатуры tools | Выводятся позже | PLAN.md |
| Выбор модели, фреймворка | Технология | PLAN.md |
| Пересказ ТЗ | Не структурировано, не проверяемо | — |
| Функции, которых нет в ТЗ | Придуманные требования | «Вне scope» или не писать |

Проверка: слова *таблица, поле, endpoint, компонент, string, number, tool, GPT, React* в онтологии — признак не того языка.

## 4. Метод — по шагам

Каждый шаг — отдельный проход по ТЗ.

### Шаг 1. Существительные → сущности

Выпиши существительные, обозначающие объекты области. Отбрось синонимы (оставь термин, который чаще в ТЗ), атрибуты под видом сущностей («дата заказа» — атрибут Заказа), технические слова («система», «интерфейс», «кнопка»).

Сущность имеет **идентичность** (конкретный экземпляр отличим от другого) и **несколько атрибутов**. Один атрибут без идентичности — это атрибут чего-то другого или перечисление.

### Шаг 2. Определения

Одно предложение на сущность, **из ТЗ или следующее из него**. Не из общих знаний. Нет определения в ТЗ → неоднозначность в раздел 10.

### Шаг 3. Атрибуты

Только упомянутые в ТЗ. Тип содержательно (*дата*, *сумма в тенге*, *одно из: черновик / отправлен / оплачен*), не технически. Перечисления выделяй явно — они станут enum в схемах.

### Шаг 4. Глаголы → действия

Для каждого действия: **кто** инициирует; **над чем**; **предусловия**; **наблюдаемый результат**; **категория** `read` / `write` / `destructive`. Из категории следует, нужно ли подтверждение.

### Шаг 5. Связи

`A -> глагол -> B` для пар, встречающихся в ТЗ вместе. Cardinality — если ТЗ позволяет. Не придумывай.

### Шаг 6. Правила

Проход по маркерам *должен, обязательно, только, не должен, запрещено, минимум, максимум, если … то*:

- **бизнес-правило** `BR-xx` — ограничение на действия или состояния;
- **инвариант** — всегда истинно;
- **валидация** `V-xx` — на вход;
- **производное значение** — формула;
- **переход состояния** — `A -> B`, включая запрещённые и необратимые.

У каждого — ссылка на место в ТЗ. Для каждого BR укажи, к какому действию оно относится — так оно попадёт в предусловие нужного tool.

### Шаг 7. Внешнее

Файлы, API, датасеты, сервисы — **только реально предоставленное**. Формат и объём, если известны.

### Шаг 8. Границы

In scope — что бот делает, конкретными глаголами и сущностями. Out of scope — что явно исключено ТЗ **и** что заманчиво добавить, но не требуется. Пиши так, чтобы по этим двум спискам можно было отсортировать любой запрос пользователя.

### Шаг 9. Критерии приёмки

`AC-xx` — наблюдаемое поведение: «пользователь делает X → видит Y». Каждый пункт критериев оценки из ТЗ порождает хотя бы один AC.

Плохо: «Реализован модуль расчёта». Хорошо: «После ввода трёх позиций итог в интерфейсе равен их сумме со скидкой».

### Шаг 10. Неоднозначности и допущения

Всё непонятное, противоречивое, отсутствующее — сюда, не в модель как факт. Неоднозначность: формулировка, где в ТЗ, трактовки, влияние. Допущение: что принято, почему, последствия, обратимость.

**Допущение никогда не пишется в разделах 1–9 как факт.**

## 5. Структура `docs/ONTOLOGY.md`

```
1. Назначение          — проблема, пользователь, результат; что бот делает — конкретно
2. Терминология        — термин: определение
3. Акторы              — кто, что делает
4. Сущности            — определение, атрибуты, перечисления, идентичность, жизненный цикл
5. Связи               — A -> отношение -> B
6. Действия            — таблица: действие · инициатор · сущности · предусловия · результат · категория
7. Правила             — BR-xx (с действием и источником); инварианты; V-xx; производные; переходы
8. Внешние данные      — только предоставленное
9. Границы             — in scope / out of scope, пригодные для классификации запросов
10. Критерии приёмки   — AC-xx
11. Неоднозначности и допущения
```

Объём 1–2 страницы. Больше трёх — в документе реализация или пересказ.

## 6. Разобранный пример

ТЗ (сокращённо): *«Сервис для кураторов учебных групп. Куратор загружает список студентов с оценками за модули. Система показывает студентов со средним баллом ниже 60 и позволяет отправить каждому напоминание. Напоминание одному студенту — не чаще раза в неделю. Пустой файл — понятная ошибка.»*

**Назначение.** Помощник куратора: показывает отстающих студентов группы по загруженным оценкам и отправляет им напоминания. Не оценивает работы, не общается со студентами от их имени, не работает с другими группами.

**Терминология.** Куратор — пользователь, ведёт группу. Студент — учащийся группы. Модуль — учебная единица с оценкой. Напоминание — сообщение куратора студенту о низком балле. Отстающий — студент со средним баллом ниже 60.

**Сущности.** Студент: ФИО, оценки по модулям; идентичность — ФИО в списке (N-01: уникального идентификатора в ТЗ нет). Оценка: модуль, балл. Напоминание: студент, дата отправки.

**Связи.** Куратор -> ведёт -> Группа (одна). Группа -> состоит из -> Студенты. Студент -> имеет -> Оценки (одна на модуль). Куратор -> отправляет -> Напоминание -> Студенту.

**Действия.**

| Действие | Инициатор | Сущности | Предусловие | Результат | Категория |
|---|---|---|---|---|---|
| Загрузить список | Куратор | Студент, Оценка | файл не пустой (V-01) | список в системе | write |
| Показать отстающих | Куратор | Студент | список загружен | студенты со средним < 60 | read |
| Отправить напоминание | Куратор | Напоминание | прошло ≥ 7 дней с прошлого (BR-02) | отправлено, дата зафиксирована | write |

**Правила.** BR-01 (Показать отстающих): отстающий = средний < 60 — п. 2. BR-02 (Отправить напоминание): не чаще раза в 7 дней — п. 3. V-01 (Загрузить): пустой файл → ошибка — п. 4. Производное: средний = сумма / число модулей. Допущение A-01: модули без оценки не учитываются; легко изменить.

**Границы.** In scope: загрузить список, показать отстающих, отправить напоминание, ответить на вопрос о балле конкретного студента. Out of scope: изменять оценки, общаться со студентами, работать с несколькими группами, давать педагогические советы.

**AC.** AC-01: после загрузки корректного файла куратор видит список студентов со средним < 60. AC-02: повторное напоминание в течение 7 дней отклоняется с сообщением, где назван BR-02. AC-03: пустой файл → понятная ошибка, система не падает.

Чего здесь **нет**: таблиц БД, tool `send_reminder`, компонента `StudentList`, слова «модель». Всё это появится в PLAN.md и будет выведено из этого текста.

## 7. Проверка перед сдачей

- [ ] Каждое требование ТЗ нашло место в модели. Проверено по ТЗ, не по памяти.
- [ ] Ничего сверх ТЗ, кроме помеченных допущений.
- [ ] Ни одна сущность не дублирует другую.
- [ ] Каждое действие имеет категорию; каждое BR привязано к действию и месту в ТЗ.
- [ ] Каждый пункт критериев оценки ТЗ покрыт хотя бы одним AC; каждый AC проверяем за минуту.
- [ ] По разделам 1 и 9 можно однозначно отсортировать десять случайных запросов пользователя на «в теме / не в теме».
- [ ] Нет технических слов из таблицы раздела 3.
- [ ] Все «наверное» вынесены в раздел 11.
- [ ] Не больше двух страниц.

Хоть один пункт не выполнен — онтология не готова.

## 8. Отчёт

Файл создан; сколько сущностей, действий, правил, AC; неоднозначности, требующие решения пользователя; допущения. **Стоп** — ждать «онтология принята».
