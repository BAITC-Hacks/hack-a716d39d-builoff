# План: «Граф денег»

## 1. Цель и режим

За один локальный запуск превратить три предоставленных Parquet в объяснимые роли всех 2 248 узлов, кластеры и ранжированный список, затем дать AML-аналитику просмотр направленной сети с поиском по `gid` (ТЗ §4–7; онтология §1, §6, AC-01–05). Режим — **pipeline + viewer**: расчёт детерминированный, диалога и действий агента нет. LLM допускается только в необязательной стадии для текстовых гипотез кластеров и карточек узлов, без влияния на роли, скоры и обязательные CSV (онтология §9–11).

## 2. Happy path

Аналитик устанавливает зависимости и запускает `python pipeline.py --data data --out out`. Команда проверяет три файла, считает метрики, кластеры, роли и приоритеты, записывает `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` и краткий итог с количеством узлов, кластеров и временем. В I2 тот же запуск создаёт `graph.json`; аналитик поднимает локальный HTTP-сервер, открывает единственный HTML viewer, вводит `gid`, видит связи со стрелками, роль, кластер и числовое объяснение (онтология §6–8, AC-01–05).

Пайплайн выполняет детерминированную валидацию входа, расчёт графа, проверку результата и запись воспроизводимых файлов с замером времени (онтология §6–9). RequestContext, Express, React/Vite, SSE, SQLite и chat postprocess не нужны для этого режима (онтология §6, §9). Необязательные структурированные LLM-вызовы добавляют только проверяемые текстовые гипотезы; роли, скоры и обязательные CSV считаются локально. Отдельный optional CLI I5 использует ограниченный agent loop с read-only tools по готовым выгрузкам (онтология §6, §9). По PROCESS.md I1 содержит CLI и CSV, а viewer достигает AC-05 в I2: I1 — работающий промежуточный результат, полная сдача требует I2. Локальные Python-команды используются для проверки и запуска; GitHub Actions удалён по явному уточнению пользователя, потому что в репозитории организатора он заблокирован.

Кластеризация — Louvain на взвешенной по `sum_kzt` неориентированной проекции с фиксированным seed 42; направление рёбер сохраняется в метриках и viewer. 19 изолированных seed получают отдельные кластеры. `sum_kzt_internal` — сумма направленных рёбер с обоими концами в кластере (онтология §11). `hypothesis` в I1 строится **после назначения ролей** шаблоном по фактическому составу ролей, seed и обороту, с осторожной формулировкой; LLM в I3 может создать альтернативный текст, но исходная гипотеза остаётся рабочей без ключа (BR-06/10).

Для BR-11 до ролей вычисляются число seed, из которых существует направленный путь к узлу, и число **других** кластеров среди соседей. Betweenness считается отдельно для каждой слабосвязной компоненты, точно, по кратчайшим направленным путям без весов: сумма KZT не является длиной пути. Топ-5% — первые `ceil(0,05 × размер)` узлов компоненты по betweenness, при равенстве — по `gid`. Приоритет ролей точно как в онтологии §7. Проверка на текущих данных: 15 узлов удовлетворяют базовым `in_deg ≥ 5 ∧ out_deg ≥ 10`, все 15 достижимы от ≥ 2 seed и связаны с ≥ 2 другими кластерами; пересчёт не использует список их `gid`.

### Шкалы и схемы результата

`clip(x) = min(1, max(0, x))`. Сила роли до штрафа: `coordinator = (clip(in_deg/10)+clip(out_deg/20))/2`; `consolidator = clip(in_deg/10)`; `distributor = clip(out_deg/20)`; `transit = clip(1 - |pass_through-1|/0,4)`; `terminal = clip(in_deg/5)`; `peripheral = 0,2`. Затем `role_score = clip(сила - 0,2 × truncated_by_depth - 0,2 × is_seed × входо-зависимая_роль)`, где входо-зависимые роли — `coordinator`, `consolidator`, `terminal` (онтология §7 BR-12). Скор означает силу наблюдаемого признака, а не вероятность правонарушения.

Для приоритета `D=clip(in_deg/10)`, `K=log(1+in_kzt)/log(1+max_in_kzt)`, `B=betweenness/max_betweenness`, `S=clip(n_reaching_seed/10)`; при нулевом знаменателе компонент равен 0. Вес роли `R`: coordinator 1; consolidator 0,9; distributor 0,8; transit 0,6; terminal 0,3; peripheral 0,1. `priority_score = clip(0,25D + 0,20K + 0,20B + 0,20S + 0,15R - 0,20 × truncated_by_depth)` (онтология §7 BR-13). Числа в `evidence`/`why` берутся из метрик именно этого `gid`; округление только для отображения. Эти веса — прозрачное рабочее допущение при отсутствии размеченных ролей (онтология §11), их не подбирают по «правильным» `gid`.

Минимальные JSON Schema строк CSV и объекта для viewer; дополнительные числовые колонки из стартера допустимы (онтология §4, §8; ТЗ §5):

```json
{
  "$defs": {
    "role": {"enum": ["coordinator", "consolidator", "distributor", "transit", "terminal", "peripheral"]},
    "score": {"type": "number", "minimum": 0, "maximum": 1},
    "nodes_roles_row": {"type": "object", "required": ["gid", "role", "role_score", "cluster_id", "priority_score", "evidence"], "properties": {"gid": {"type": "integer"}, "role": {"$ref": "#/$defs/role"}, "role_score": {"$ref": "#/$defs/score"}, "cluster_id": {"type": "integer"}, "priority_score": {"$ref": "#/$defs/score"}, "evidence": {"type": "string", "minLength": 1, "maxLength": 200}}},
    "clusters_row": {"type": "object", "required": ["cluster_id", "n_nodes", "n_seed", "sum_kzt_internal", "top_gids", "hypothesis"], "properties": {"cluster_id": {"type": "integer"}, "n_nodes": {"type": "integer", "minimum": 1}, "n_seed": {"type": "integer", "minimum": 0}, "sum_kzt_internal": {"type": "number", "minimum": 0}, "top_gids": {"type": "string"}, "hypothesis": {"type": "string", "minLength": 1}}},
    "top_nodes_row": {"type": "object", "required": ["rank", "gid", "role", "priority_score", "why"], "properties": {"rank": {"type": "integer", "minimum": 1}, "gid": {"type": "integer"}, "role": {"$ref": "#/$defs/role"}, "priority_score": {"$ref": "#/$defs/score"}, "why": {"type": "string", "minLength": 1}}},
    "graph": {"type": "object", "required": ["nodes", "edges"], "properties": {"nodes": {"type": "array", "items": {"type": "object", "required": ["id", "gid", "role", "cluster_id", "priority_score"], "properties": {"id": {"type": "string"}, "gid": {"type": "integer"}, "role": {"$ref": "#/$defs/role"}, "cluster_id": {"type": "integer"}, "priority_score": {"$ref": "#/$defs/score"}}}}, "edges": {"type": "array", "items": {"type": "object", "required": ["id", "source", "target", "sum_kzt", "n_tx"], "properties": {"id": {"type": "string"}, "source": {"type": "string"}, "target": {"type": "string"}, "sum_kzt": {"type": "number", "minimum": 0}, "n_tx": {"type": "integer", "minimum": 1}}}}}}
```

CSV сохраняют точные заголовки ТЗ; `graph.json` содержит те же идентификаторы, роли и направленные рёбра, без добавления клиентских атрибутов. При необязательном LLM-вызове его структурированный результат имеет только `cluster_id`, `hypothesis`, `supporting_gids` либо `gid`, `summary`, `metrics_used`; проверка подтверждает существование всех `gid` и каждого числа в исходных метриках, иначе сохраняется детерминированный текст (BR-10).

## 5. Достоверность, ошибки, состояние

BR-01, BR-02, BR-03 и V-01–03 проверяются при загрузке; BR-02 и BR-05 — при построении метрик; BR-06 и BR-11 — при кластерах и выборе роли; BR-04 и BR-12 — при назначении роли; BR-07 и BR-13 — при ранжировании; BR-04, BR-06, BR-07 и BR-09 — при выгрузке; BR-08 — в viewer; BR-10 — во всех пользовательских текстах. Перечисление шести ролей из онтологии §4 переходит в схемы CSV/JSON; прочие роли не появляются без документированного расширения. Ontology check не включён: пользователь не задаёт свободные запросы. Нет данных/битый файл/неизвестный `gid` → явное сообщение, без выдуманных результатов; отсутствующий LLM-ключ не влияет на обязательный путь.

Ошибки входа: отсутствующий файл, неверные колонки/типы, дубли `gid`, неизвестный конец ребра, выходящая за окно дата или глубина, расхождение агрегата — CLI завершает работу ненулевым кодом с указанием файла и правила V/BR, не оставляя частичный комплект CSV. Пустой датасет — та же ошибка. Неправильный `gid` в viewer показывает «узел не найден», не ломая схему. Данные внутри файлов рассматриваются как данные: инструкции в строках и LLM-тексте не исполняются (BR-10).

Persistence — только входные Parquet и выходные CSV/JSON на диске; пользовательских сессий и БД нет. В памяти расчёта находятся граф, метрики и кластеры. Нет confirmation, guard, chat postprocess и SSE: в онтологии §6 нет destructive-действий, свободного чата и долгой интерактивной обработки. Проверка выхода детерминированно сверяет схемы, счётчики, диапазоны скоров, покрытие узлов и кластеров, порядок top и наличие объяснений; отдельный LLM-check не нужен.

## 6. Риски и ограничения

- `starter/starter.py` вызывает `nx.pagerank`, которому в проверенной среде потребовался SciPy, отсутствующий в `starter/requirements.txt`. I1 добавляет его в собственный список зависимостей и проверяет чистую установку.
- 19 seed не попадают в граф, если строить его только по рёбрам; 444 узла на depth 4 ложно выглядели бы terminal. I1 явно учитывает оба случая (BR-02/05, AC-02–04).
- Louvain на неориентированной проекции используется только для группировки; роли, пути, betweenness и показанные стрелки сохраняют направление. Число сообществ может зависеть от версии библиотеки, поэтому фиксируются версии и seed; «67» — наблюдение, не AC.
- Browser `file://` обычно не читает соседний JSON через `fetch`; I2 включает запуск локального `python -m http.server`, а Cytoscape.js хранится локально, без обязательного интернета.
- Отсутствуют переводы ниже 5 000 KZT и вне банка/периода; `terminal`, координатор и приоритет — гипотезы по частичному графу, не AML-вердикт (BR-01/05/10).
- LLM API, его задержка и стоимость не могут блокировать AC; I3 выполняется только при наличии ключа, ошибка видна явно, детерминированные выгрузки остаются доступными.

## 8. README и сдача

Финальный README следует 11 заголовкам AGENTS.md, но команды и доказательства соответствуют Python pipeline, а не chat: точные версии библиотек и Cytoscape.js, одна команда расчёта, запуск локального viewer, схемы трёх CSV, критерии ролей и ограничение данных, раздел о масштабировании до ~1 млн узлов (ТЗ §9–10). `docs/EVIDENCE.md` содержит **реальные** stdout запуска и проверок, фрагменты CSV для произвольных `gid`, временной замер, edge cases и скриншоты viewer; нет выдуманного «демо-диалога», которого продукт не ведёт. Схема «данные → метрики → роли/кластеры → viewer» и пятиминутный demo script закрывают артефакты ТЗ §10. Данные и происхождение стартера раскрываются; секреты только в env, LLM-ключ не нужен для AC. Чистый клон повторяет инструкцию до просмотра узла. Публичный деплой не обязателен и не планируется до проверки условий использования предоставленных данных; при отсутствии URL README честно говорит «не развёрнуто».

## 9. Design review: ТЗ ↔ онтология ↔ план

| Требование | Онтология | Этап и проверка |
|---|---|---|
| Три CSV за < 5 минут одним запуском | BR-01–03/09, AC-01 | I1 T1.1/1.2/1.5/1.6, чистая установка и замер |
| Роль, скор, evidence у 2 248 узлов, без ложных terminal на depth 4 | BR-02/04/05/11/12, AC-02/03 | I1 T1.2/1.4, проверки всех строк и разбор 3 `gid` |
| Кластеры и изоляты | BR-02/06/11, AC-04 | I1 T1.3, покрытие и сводки |
| Ранжирование ≥ 20 и объяснение | BR-07/13, AC-05 | I1 T1.5, схема/сортировка/числа |
| Поиск на направленной схеме с ролями | BR-08, AC-05 | I2 T2.1–2.3, просмотр 3 `gid` |
| Осторожность, приватность, ограничения | BR-01/05/10 | I1 evidence/гипотезы; I2 карточка; I3 grounding; README |
| Optional время и LLM | онтология §9, ТЗ §8 | I3 T3.1–3.3, без блокировки AC |

Зависимости не цикличны: в I1 кластеры вычисляются до `coordinator`, затем роли до приоритета; в I2 viewer читает уже вычисленное; I3 не меняет обязательный путь. Все BR имеют этап проверки, все пять AC имеют задачу и наблюдаемую проверку. Единственное сознательное расхождение с общим шаблоном PROCESS.md — I1 ещё без viewer по явному расписанию пользователя; сдаваемый must-have закрывается I2 до 16:00. За пределами ТЗ не добавлены чат, личные данные или управление банковскими счетами.
